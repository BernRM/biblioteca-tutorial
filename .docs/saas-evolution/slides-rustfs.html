1 · O problema

Alguém envia a capa de um livro. Onde ela fica?

Os bytes de uma imagem precisam morar em algum lugar. As duas primeiras ideias são as mais comuns, e as duas têm problemas.

Pergunte à turma antes de avançar: "onde vocês guardariam?". Quase todo mundo responde disco ou banco. As próximas telas mostram por que nenhum dos dois escala bem.

1 · O problema

Opção 1: gravar no disco do servidor

// recebe o upload e grava numa pasta local
const file = form.get("capa") as File;
await Bun.write(`uploads/${id}.jpg`, file);

Funciona no seu computador. É a primeira coisa que todo mundo tenta.

  • O contêiner é recriado a cada deploy. Sem volume, as fotos vão embora junto.
  • O disco do servidor enche. Aumentar costuma exigir parar a máquina.
  • O backup do banco não inclui a pasta uploads/: são dois backups para manter em sincronia.
  • E quando a aplicação tiver duas cópias rodando?
O ponto central não é "disco é ruim": é que o arquivo fica preso a UMA máquina. O último item puxa a próxima tela.

1 · O problema

Duas instâncias atrás de um balanceador

Com duas instâncias, cada disco vira uma ilha. O arquivo precisa ficar num lugar que todas enxerguem.

Passo a passo: o upload cai na A e fica no disco A. A próxima leitura cai na B (o balanceador escolhe), e a B não tem o arquivo: 404. Isso acontece de verdade assim que se escala horizontalmente.

1 · O problema

Opção 2: guardar os bytes numa coluna do banco

ALTER TABLE livros ADD COLUMN capa BYTEA;

UPDATE livros SET capa = $1 WHERE id = 7;
  • Todas as instâncias enxergam o mesmo banco.
  • Entra na mesma transação do livro.
  • O banco incha: backup e restauração ficam lentos por causa de imagens que nunca mudam.
  • Cada imagem exibida ocupa uma conexão do banco, que é um recurso escasso.
  • O disco do banco é o mais caro da infraestrutura.
  • Uma CDN não consegue servir a imagem direto do banco.
BLOB no banco resolve o problema das ilhas, mas usa a peça mais cara e mais disputada da arquitetura para guardar bytes que só são lidos. Vale para poucos arquivos pequenos; não escala para mídia.

1 · O problema

O que queremos de um lugar para arquivos

  • Compartilhado: qualquer instância lê e grava.
  • Cresce sem planejar disco: terabytes, petabytes.
  • Acessível por HTTP, de qualquer linguagem.
  • Barato por gigabyte e durável (cópias, redundância).
  • Com metadados: tipo, tamanho, data.
  • Separado do banco: o banco guarda só a referência.

Isso tem nome: armazenamento de objetos (object storage).

Leia os requisitos como uma lista de desejos. O último item é a regra que vamos repetir a aula toda: no banco fica a referência; os bytes ficam no armazenamento de objetos.

2 · Três jeitos de guardar dados

Bloco, arquivo e objeto

Bloco

O disco “cru”, dividido em blocos numerados. Quem organiza é o sistema operacional ou o banco.

Ex.: o volume do Postgres, o disco de uma VM.

Arquivo

Pastas e caminhos. Dá para abrir, editar um trecho no meio e travar o arquivo.

Ex.: o disco do seu computador, uma pasta compartilhada na rede.

Objeto

Uma chave aponta para os bytes e os metadados, tudo por HTTP. Não há pastas de verdade nem edição no meio.

Ex.: Amazon S3, Cloudflare R2, RustFS.

Três níveis de abstração. Bloco: o disco cru. Arquivo: o que vocês usam todo dia. Objeto: um serviço HTTP onde cada coisa guardada tem uma chave. A próxima tela traz uma analogia para o objeto.

2 · Três jeitos de guardar dados

Um objeto é como um carro com manobrista

o carrosão os bytes do arquivo
o tíqueteé a chave do objeto
o manobristaé a API: você nunca entra no estacionamento
Avance devagar. (1) Você entrega o carro. (2) Recebe um tíquete: A7F3. (3) O carro some numa vaga que você não conhece e nem precisa conhecer. (4) Você devolve o tíquete e o carro volta. (5) O mapa: carro = bytes, tíquete = chave, manobrista = API HTTP. Você nunca anda pelo estacionamento: não há "pastas" para navegar.

3 · Anatomia

O que tem dentro de um objeto

bucket · biblioteca
chavelivros/7/capa
dados
89504E470D0A1A0A00…

7.853 bytes: a imagem inteira, sem interpretação

metadados
Content-Type: image/png
Content-Length: 7853
ETag: "36bbd90a…"
Last-Modified: 12 nov 2026 15:54
  • Chave: o nome único do objeto dentro do bucket. É o “tíquete”.
  • Dados: os bytes, do jeito que chegaram. O serviço não abre nem entende a imagem.
  • Metadados: informações sobre os bytes, como tipo, tamanho, uma impressão digital (ETag) e a data.
  • Bucket: o “estacionamento” onde o objeto mora.
Um objeto tem três partes: chave, dados e metadados. Ele mora num bucket. O serviço trata os dados como uma caixa-preta de bytes: quem sabe que aquilo é PNG é o Content-Type.

3 · Anatomia

Bucket e chave: o endereço do objeto

Bucket

  • O recipiente de mais alto nível. Todo objeto mora num bucket.
  • Tem nome (biblioteca, biblioteca-test) e regras próprias, como quem pode acessar.
  • Na AWS, o nome é global: ninguém mais pode criar um bucket com o mesmo nome.

Chave

  • Um texto qualquer, de até 1.024 bytes, que identifica o objeto no bucket.
  • Gravar de novo na mesma chave substitui o objeto.
  • Quem escolhe a chave é o servidor, nunca o usuário: livros/7/capa

bucket + chave = o endereço único de um objeto

Reforce: a chave é decidida pelo servidor. Usar o nome do arquivo que o usuário mandou abre espaço para colisões ("foto.jpg" de duas pessoas) e para nomes maliciosos.

3 · Anatomia

Não existem pastas. Existem prefixos.

o que o serviço guarda: uma lista plana de chaves

autores/3/foto
livros/12/capa
livros/7/capa
livros/8/capa
relatorios/2026/11/acervo.pdf

A lista vem em ordem de texto: livros/12 aparece antes de livros/7.

o que o console desenha

autores/
   3/ foto
livros/
   12/ 7/ 8/
relatorios/ …

LIST com prefix=livros/ devolve só as chaves que começam assim.

A barra / é só um caractere. Apague o último objeto com aquele prefixo e a “pasta” some sozinha.

O console desenha pastas para ajudar a navegar, mas o armazenamento é plano: uma tabela chave → objeto. A barra é convenção. Por isso não existe "criar pasta vazia" no S3 (alguns consoles simulam criando um objeto vazio).

3 · Anatomia

Metadados, e por que um objeto não se edita

MetadadoPara que serve
Content-Typeo tipo: image/png. O navegador usa para exibir.
Content-Lengtho tamanho, em bytes
ETaguma impressão digital: mudou o conteúdo, muda a ETag
Last-Modifiedquando foi gravado
x-amz-meta-*metadados seus, por exemplo x-amz-meta-livro: 7

versão 1 · livros/8/capa

type: image/png
size: 12
etag: "36bbd90a…ed8f"

gravou de novo · mesma chave

type: image/jpeg
size: 6
etag: "e4cc473c…4dc1"

Não existe “mudar a linha 3 do objeto”. Grava-se tudo de novo, e o objeto antigo é substituído por inteiro.

Os números da direita são reais, do nosso teste com o RustFS: a mesma chave recebeu um PNG e depois um JPEG. O tipo, o tamanho e a ETag mudaram juntos. Objeto é imutável: trocar = gravar de novo.

4 · A API HTTP

Cada objeto tem um endereço HTTP

http://localhost:9000/biblioteca/livros/7/capa
endpoint
onde o serviço atende
bucket
o primeiro trecho do caminho
chave
o resto do caminho, com as barras

Na AWS, o bucket também pode ir no nome do host: https://biblioteca.s3.amazonaws.com/livros/7/capa. É o mesmo objeto, escrito de outro jeito.

Se o objeto é um recurso HTTP, os verbos HTTP fazem o resto: PUT, GET, HEAD, DELETE.

O formato da primeira linha é o "path-style", que o RustFS usa por padrão. O formato com o bucket no host é o "virtual-hosted style" da AWS. Para o código, tanto faz: o cliente S3 monta a URL.

4 · A API HTTP

PUT grava um objeto

requisição

PUT /biblioteca/livros/7/capa HTTP/1.1 Host: localhost:9000 Content-Type: image/png Content-Length: 7853 Authorization: AWS4-HMAC-SHA256 … ‰PNG␍␊␚␊ … (7.853 bytes)

resposta

HTTP/1.1 200 OK ETag: "36bbd90a8f515b48…"

Gravou. Se a chave já existia, o objeto antigo foi substituído.

O corpo da requisição são os bytes crus, sem JSON e sem base64. O Content-Type enviado vira metadado do objeto. O Authorization é a assinatura: vamos abri-la na parte de segurança.

4 · A API HTTP

GET lê um objeto

GET /biblioteca/livros/7/capa HTTP/1.1 Host: localhost:9000 Authorization: AWS4-HMAC-SHA256 …
HTTP/1.1 200 OK Content-Type: image/png Content-Length: 7853 ‰PNG␍␊␚␊ … (7.853 bytes)
GET /biblioteca/livros/999/capa HTTP/1.1
HTTP/1.1 404 Not Found <Code>NoSuchKey</Code>
A resposta devolve os bytes e o Content-Type gravado no PUT. Chave inexistente: 404 com o código NoSuchKey no corpo XML. Esse nome volta no código Bun, como error.code.

4 · A API HTTP

HEAD consulta, DELETE apaga

HEAD: só os metadados

HEAD /biblioteca/livros/7/capa
HTTP/1.1 200 OK Content-Type: image/png Content-Length: 7853 (sem corpo)

Responde “existe?” e “qual o tipo?” sem baixar os bytes.

DELETE: apaga

DELETE /biblioteca/livros/7/capa
HTTP/1.1 204 No Content

Apagar de novo? 204 outra vez. Apagar uma chave que não existe não é erro: o DELETE é idempotente.

HEAD é o que os métodos exists() e stat() do Bun fazem por baixo. O DELETE idempotente simplifica o código: não precisa checar antes de apagar.

4 · A API HTTP

LIST: as chaves que começam com um prefixo

GET /biblioteca?list-type=2&prefix=livros/
  • É um GET no bucket, não num objeto.
  • Devolve até 1.000 chaves por vez. Para mais, pede-se a próxima página.
  • Não traz os bytes, só a lista de chaves.
<ListBucketResult>
  <Name>biblioteca</Name>
  <Prefix>livros/</Prefix>
  <Contents>
    <Key>livros/7/capa</Key>
    <Size>7853</Size>
  </Contents>
  <Contents>
    <Key>livros/8/capa</Key>
    <Size>1346</Size>
  </Contents>
  <IsTruncated>false</IsTruncated>
</ListBucketResult>
A resposta é XML. Ninguém lê XML à mão: o cliente S3 converte em objetos. IsTruncated=true indica que há mais páginas.

4 · A API HTTP

S3: a língua comum do armazenamento de objetos

Em 2006, a Amazon lançou o S3 com essa API HTTP. Como muita gente passou a usar, outros serviços copiaram a mesma API.

Amazon S3Cloudflare R2Backblaze B2DigitalOcean SpacesWasabiCeph RGWGarageSeaweedFSMinIORustFS

o mesmo código; só o endpoint muda

new S3Client({ endpoint: "https://s3.us-east-1.amazonaws.com", … });       // Amazon S3
new S3Client({ endpoint: "https://<conta>.r2.cloudflarestorage.com", … }); // Cloudflare R2
new S3Client({ endpoint: "http://localhost:9100", … });                    // o RustFS local

Aprender S3 com o RustFS na sua máquina vale para a nuvem também.

Este é o argumento prático: o que a turma aprender hoje com o RustFS local serve para AWS, R2 e companhia. A compatibilidade de cada serviço é ampla, não total; o básico (PUT, GET, HEAD, DELETE, LIST, URLs assinadas) é igual em todos.

5 · Segurança

Privado por padrão: toda requisição prova quem é

Access key: quem é você

Funciona como um nome de usuário. Viaja em toda requisição e pode aparecer em logs.

exemplo

Secret key: a prova

Funciona como uma senha, mas nunca viaja. Serve só para assinar a requisição.

exemplo-secreto

o cabeçalho de uma requisição de verdade

Authorization: AWS4-HMAC-SHA256 Credential=exemplo/20261112/us-east-1/s3/aws4_request, SignedHeaders=host;x-amz-content-sha256;x-amz-date, Signature=25d0ac9d2a4990dbd4445470dc417f984be58cb60d327d6264fe0aa844912354

A access key está ali, e a secret não. No lugar dela vai uma assinatura calculada com ela. Sem assinatura válida, a resposta é 403.

Mostre que a secret key não aparece no cabeçalho. O nome AWS4-HMAC-SHA256 é o algoritmo de assinatura do S3 (SigV4), que todos os compatíveis implementam.

5 · Segurança

A assinatura funciona como um carimbo

Intuição, sem matemática: o carimbo depende do conteúdo da requisição E do segredo. Quem não tem o segredo não consegue produzir o carimbo certo. Mudou uma vírgula, o carimbo não bate. A data entra no cálculo, então uma requisição capturada não serve para sempre. (Tecnicamente: SigV4, HMAC-SHA256 com uma chave derivada da secret, da data, da região e do serviço.)

5 · Segurança

URL pré-assinada: o carimbo vai dentro da URL

http://localhost:9000/biblioteca/livros/7/capa ?X-Amz-Algorithm=AWS4-HMAC-SHA256 &X-Amz-Credential=exemplo/20261112/auto/s3/aws4_request &X-Amz-Date=20261112T155417Z &X-Amz-Expires=900 &X-Amz-SignedHeaders=host &X-Amz-Signature=25d0ac9d2a4990dbd4445470dc417f98…
  • Credential: a access key. A secret continua no servidor.
  • Date + Expires: vale 900 segundos (15 minutos) a partir daquele instante.
  • Signature: o carimbo. Mudou qualquer parâmetro, ele deixa de valer.
  • Quem tem a URL, tem o acesso, até ela expirar. O navegador abre direto, sem senha.
O servidor que tem a secret gera a URL (em Bun: s3.presign). Ele entrega a URL a quem deve acessar. O formato foi copiado de uma URL que o Bun gerou no nosso teste contra o RustFS (só troquei o host pelo padrão 9000).

5 · Segurança

Dois caminhos para mostrar uma imagem

A · pelo backend

  • O RustFS fica escondido na rede interna.
  • Validação e permissão no mesmo lugar.
  • Cada imagem ocupa o servidor da aplicação.

B · URL assinada

  • O servidor nem toca nos bytes.
  • Combina com CDN.
  • O armazenamento precisa ser alcançável pelo navegador.

Hoje, na biblioteca, vamos de A: o RustFS fica só na rede interna do compose e o backend valida tudo. É o caminho mais simples para aprender.

Os dois caminhos são corretos. A é mais simples e esconde o armazenamento; B tira peso do servidor e escala melhor. A próxima tela mostra o que fazer em produção.

5 · Segurança · em produção

Em produção: um subdomínio só para mídia, com URLs de validade curta

importante
  • O servidor da aplicação não carrega bytes de imagem e fica livre para a API.
  • A CDN guarda cópias perto do usuário: a imagem chega mais rápido e o bucket recebe menos acessos.
  • Os cookies de sessão de app. não viajam em cada imagem, porque é outro host.
  • O que os usuários enviam fica numa origem separada: um arquivo malicioso não roda com os privilégios da aplicação.
  • Validade curta (minutos): um link vazado expira logo.
Este é o recado de arquitetura para levar para a vida. Na aula fazemos pelo backend porque é mais simples e mantém o RustFS escondido. Em produção, o ideal é um subdomínio próprio servindo as imagens direto, com URLs assinadas de validade curta e uma CDN na frente. Detalhe dos cookies: eles só deixam de ir junto se forem "host-only" (sem Domain=biblioteca.com).

6 · Quando usar

Quando usar, e quando não usar

Use para

  • Imagens, vídeos, áudio e PDFs enviados por usuários
  • Backups e exportações
  • Logs e arquivos de dados para análise
  • Arquivos estáticos de sites e resultados de build

Não use para

  • Dados que você filtra e consulta: isso é tarefa do banco
  • Editar um pedaço do arquivo: o objeto se substitui inteiro
  • Muitas escritas por segundo no mesmo objeto
  • Transações que envolvem vários objetos

No banco, a referência. No armazenamento de objetos, os bytes.

A frase do banner é a regra de ouro da aula. Na biblioteca, a tabela livros vai guardar só a informação de que existe uma capa (uma data); os bytes ficam no RustFS.

Durante anos, o MinIO foi o servidor S3 aberto mais usado para rodar localmente e em servidores próprios. Entre 2025 e 2026, isso mudou:

7 · O RustFS

Um nó para aprender, vários nós para produção

Para a aplicação, nada muda: o mesmo endpoint e as mesmas chamadas S3. O que muda é quantas falhas o armazenamento aguenta.

No compose usamos um nó com um disco (um volume do Docker). Em produção, vários nós com vários discos cada. Como os dados se espalham entre os discos é o assunto das duas próximas telas.

7 · O RustFS

Erasure coding: fatiar o objeto e espalhar pelos discos

(1) O objeto é fatiado em 4 pedaços de dados. (2) A partir deles, calculam-se 2 pedaços de paridade: informação extra que permite reconstruir o que faltar. (3) Cada pedaço vai para um disco diferente. A proporção 4+2 é só um exemplo; ela é configurável.

7 · O RustFS

Dois discos caem, e o objeto continua inteiro

Com 4 fatias de dados e 2 de paridade, quaisquer 4 das 6 bastam: até 2 discos podem falhar.

Em aula, com 1 nó e 1 disco, não existe essa proteção: o volume é a única cópia. Fora da aula, isso se resolve com backup ou com vários discos.

Ponto-chave: a paridade troca espaço por tolerância a falhas, sem precisar guardar cópias inteiras. Termine com o alerta: o nosso RustFS de aula não tem redundância nenhuma.

O serviço rustfs

    environment:

      RUSTFS_ACCESS_KEY: exemplo

imagem fixa

A access key e a secret key do servidor. Em aula ficam no arquivo; em produção vêm de segredos.

duas portas

9000: a API S3. 9001: o console web. Aqui elas aparecem como 9100 e 9101 no seu computador.

Diferente de um cache, os objetos são a fonte da verdade: precisam sobreviver ao contêiner.

Pergunta se o servidor está pronto, não só se está vivo. A próxima tela mostra por quê.

Percorra linha a linha. As portas 9100 e 9101 foram escolhidas para não colidir com outro MinIO ou RustFS que alguém já tenha rodando na 9000 e na 9001. Dentro da rede do compose, o serviço continua atendendo na 9000.

8 · RustFS no Docker

“Vivo” não é o mesmo que “pronto”

Na primeira versão do exemplo, o healthcheck usava /health. O compose deu o RustFS como saudável, o rc tentou criar o bucket e levou 503.

Com /health/ready, quem depende do RustFS só começa quando a API S3 aceita requisições. Liveness: está vivo? Readiness: já atende?

História real, do teste que fizemos para preparar esta aula: o init falhou com "Network error: Service error: unhandled error (status: 503)". A documentação do RustFS explica: as rotas de saúde respondem antes de a inicialização terminar, e a API S3 devolve 503 até o servidor ficar "FullReady". Os tempos do gráfico são aproximados (cerca de 10 s numa máquina comum).

8 · RustFS no Docker · compose.yaml

Quem cria o bucket: uma tarefa que roda uma vez

  # Tarefa única: cria o bucket com o rc, o cliente de linha de comando que já
  # vem dentro da imagem do RustFS. Rodar de novo não dá erro (--ignore-existing).
  criar-bucket:
    image: rustfs/rustfs:1.0.5
    depends_on:
      rustfs:
        condition: service_healthy
    entrypoint: ["/bin/sh", "-c"]
    command:
      - |
        rc alias set local http://rustfs:9000 exemplo exemplo-secreto
        rc bucket create --ignore-existing local/fotos

Usa a mesma imagem do RustFS, que já traz o rc, o cliente de linha de comando, e troca o comando de entrada por um shell.

rc alias set guarda o endereço e as chaves. rc bucket create --ignore-existing cria o bucket, e rodar de novo não dá erro.

Só começa quando o rustfs está pronto, graças ao healthcheck da tela anterior.

Por que um serviço só para isso? O cliente S3 do Bun lê e grava objetos, mas não cria buckets. Deixar o bucket no compose torna o ambiente reprodutível: docker compose down -v e up recriam tudo sozinhos.

9 · O cliente S3 do Bun

write: gravar um objeto

const png = await Bun.file("capa.png").bytes();

  • É um PUT. O type vira o Content-Type do objeto.

9 · O cliente S3 do Bun

file não busca nada; stat e exists perguntam

const file = s3.file("livros/7/capa"); // só uma referência: nenhuma requisição ainda

await file.stat(); // HEAD
// S3Stat {
//   etag: "\"36bbd90a8f515b48cafb94118844ed8f\"",
//   lastModified: 2026-11-12T15:54:16.000Z,
//   size: 12,
//   type: "image/png",

await s3.exists("livros/7/capa");   // true
await s3.exists("livros/999/capa"); // false

stat() numa chave que não existe lança erro (NoSuchKey). Já exists() responde false.

A saída do stat é real (o objeto de teste tinha 12 bytes). O s3.file é "preguiçoso": é só um ponteiro, e a rede só é usada quando você chama stat, bytes ou stream.

9 · O cliente S3 do Bun

Ler o conteúdo: tudo de uma vez ou em pedaços

bytes(): tudo na memória

const bytes = await file.bytes();
bytes.length; // 7853

Simples. Mas um vídeo de 2 GB ocuparia 2 GB de memória.

stream(): em pedaços

const { type } = await file.stat();
return new Response(file.stream(), {
  headers: { "Content-Type": type },
});

Os pedaços chegam do RustFS e saem para o navegador. O servidor nunca segura o arquivo inteiro. A resposta vai em chunked, sem Content-Length.

Para devolver uma imagem numa rota HTTP, use stream.

Ler uma chave inexistente com bytes() também lança S3Error com code NoSuchKey (testado). Por isso, no mini-app, o stat vem antes: ele dá o Content-Type e já descobre se o objeto existe.

9 · O cliente S3 do Bun

list, delete e presign

const { contents } = await s3.list({ prefix: "fotos/" });
// [{ key: "fotos/b888edc9-….png", size: 7853, … }]   até 1.000 por chamada

await s3.delete("fotos/b888edc9-….png");
await s3.delete("fotos/nao-existe.png"); // também não dá erro

const download = s3.presign("fotos/b888edc9-….png", { expiresIn: 300 });
const upload = s3.presign("fotos/nova.png", { method: "PUT", expiresIn: 300 });
  • list é o LIST por prefixo; para mais de 1.000 chaves, pede-se a próxima página.
  • presign não faz requisição: só calcula a URL assinada. Sempre passe expiresIn, porque o padrão é 24 horas.
O presign gera URLs de GET por padrão; com method: "PUT" o navegador pode enviar um arquivo direto ao armazenamento. Hoje não vamos usar, mas é o caminho B (e o de produção) da parte de segurança.

Um programa renomeado para foto.jpg começa com 4D 5A (“MZ”). Nenhuma assinatura bate, e a resposta é 400, seja qual for a extensão ou o Content-Type que o navegador mandou.

Esses bytes iniciais são chamados de "magic numbers". O nome do arquivo e o Content-Type do multipart são escolhidos por quem envia, e por isso podem mentir. No WebP, a parte que identifica o formato começa no byte 8, depois de RIFF e de 4 bytes de tamanho. No teste, um arquivo começando com MZ recebeu 400.

10 · Mini-app · index.ts

Passo 2: a tabela de assinaturas e a função que detecta o tipo

// 2. Validação: o tipo vem dos primeiros bytes do arquivo (a "assinatura"),
//    nunca do nome nem do Content-Type que o navegador mandou.
const MAX_BYTES = 2 * 1024 * 1024;

const SIGNATURES = [
  { type: "image/jpeg", ext: "jpg", offset: 0, bytes: [0xff, 0xd8, 0xff] },
  { type: "image/png", ext: "png", offset: 0, bytes: [0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a] },
  // WebP: "RIFF" no início e "WEBP" a partir do byte 8
  { type: "image/webp", ext: "webp", offset: 8, bytes: [0x57, 0x45, 0x42, 0x50] },
];

function detectImage(bytes: Uint8Array) {
  return SIGNATURES.find((s) => s.bytes.every((b, i) => bytes[s.offset + i] === b)) ?? null;
}

2 × 1024 × 1024 = 2 MB. O limite fica numa constante com nome.

Cada formato diz seu tipo, sua extensão, onde a assinatura começa (offset) e quais bytes esperar.

find procura a primeira assinatura cujos bytes batem. Se nenhuma bater, devolve null.

Esta tabela é o "porteiro" do upload. Para aceitar um formato novo, basta uma linha a mais, sem mexer no resto.

10 · Mini-app · index.ts

Passo 4: o upload, uma verificação por linha

      // POST: recebe o multipart, valida e grava o objeto
      POST: async (req) => {
        const form = await req.formData();
        const file = form.get("foto");
        if (!(file instanceof File)) return Response.json({ error: "Envie o campo foto" }, { status: 400 });
        if (file.size > MAX_BYTES) return Response.json({ error: "A foto passa de 2 MB" }, { status: 413 });

        const bytes = new Uint8Array(await file.arrayBuffer());
        const image = detectImage(bytes);
        if (!image) return Response.json({ error: "Envie JPEG, PNG ou WebP" }, { status: 400 });

        // a chave é escolhida pelo servidor: nada do nome original entra nela
        const key = `fotos/${crypto.randomUUID()}.${image.ext}`;
        await s3.write(key, bytes, { type: image.type });
        return Response.json({ chave: key }, { status: 201 });
      },

formData() lê o multipart. Sem o campo foto, ou se não for arquivo: 400.

Maior que 2 MB: 413 Payload Too Large, antes de ler os bytes.

Lê os bytes e confere a assinatura. Não é JPEG, PNG nem WebP: 400.

A chave é um UUID com a extensão detectada. Nada do nome original entra nela.

s3.write com o tipo detectado (é o PUT), e a resposta é 201 com a chave.

O comentário da linha 41 fala em PUT porque é o que acontece no RustFS; a rota HTTP do mini-app é POST. Peça à turma para apontar onde estaria uma falha de segurança se a chave usasse file.name.

10 · Mini-app de fotos

O caminho de uma leitura

Duas idas ao RustFS: o stat (HEAD) traz o tipo e confirma que existe, e o stream (GET) traz os bytes. Os pedaços passam pelo Bun sem que ele monte o arquivo inteiro na memória.

10 · Mini-app · index.ts

Passo 5: ler e devolver os bytes

    "/fotos/:nome": {
      // GET: lê do RustFS e devolve os bytes, com o Content-Type gravado no upload
      GET: async (req) => {
        const key = `fotos/${req.params.nome}`;
        const file = s3.file(key);
        try {
          const { type } = await file.stat();
          // Atenção: new Response(file) responderia 302 para uma URL assinada
          // do RustFS. Aqui queremos que os bytes passem pelo servidor.
          return new Response(file.stream(), { headers: { "Content-Type": type } });
        } catch (error) {
          if ((error as { code?: string }).code === "NoSuchKey") return new Response("Não encontrada", { status: 404 });
          throw error;
        }
      },

Monta a chave a partir do parâmetro da rota. O s3.file ainda não fez nenhuma requisição.

stat(): o tipo gravado no upload. De quebra, descobre se o objeto existe.

stream() com o Content-Type certo, e não new Response(file), que viraria um 302.

NoSuchKey vira 404. Qualquer outro erro sobe: é um problema de verdade.

Aqui aparece a armadilha do 302 na prática: o comentário das linhas 66 e 67 está no código de propósito. Por que não há Content-Length? No Bun 1.4.4, o stream de um arquivo do S3Client sai sempre com Transfer-Encoding: chunked, e o Bun descarta um Content-Length escrito à mão. O navegador exibe a imagem do mesmo jeito.

O bucket é compartilhado por todas as instâncias e cresce sem planejar disco. O disco local vira ilha, e o BYTEA incha o banco.

A chave, escolhida pelo servidor. A ETag é uma impressão digital do conteúdo: muda quando os bytes mudam, então não serve de nome.
