O RustFS no compose

Até aqui, tudo o que a aplicação guarda cabe numa linha de tabela. Uma imagem não cabe bem: são centenas de kilobytes que ninguém consulta com WHERE. Num bytea do Postgres, ela incha o banco, os backups e cada consulta que traz a linha inteira. No disco do contêiner, ela some quando o contêiner é recriado e não aparece para uma segunda instância da aplicação.

O lugar dela é um armazenamento de objetos: um serviço que guarda arquivos inteiros, cada um sob uma chave, dentro de um bucket, e que fala a API S3, a mesma do serviço da Amazon. O RustFS é uma implementação aberta dessa API, escrita em Rust, que roda num contêiner. O mesmo código funciona amanhã contra o S3 da Amazon, o R2 da Cloudflare ou um MinIO.

ServiçoO que guardaVolume?
Postgresos registros: livros, autores, empréstimos e, agora, quando a capa mudousim, pgdata
Redisdados derivados: cache e índice vetorialnão: o servidor reconstrói tudo a partir do Postgres
RustFSos bytes das capassim, rustfsdata: uma capa perdida não se reconstrói

Cada decisão desse trecho tem um motivo:

  • Há volume. O Redis da aula anterior não tinha, de propósito: tudo nele deriva do Postgres. Com o RustFS é o contrário. Os bytes de uma capa só existem ali, então o bucket também é fonte da verdade.
  • Só o console é publicado, e só em 127.0.0.1. A API S3 (porta 9000) fica na rede interna do Docker: a aplicação fala com http://rustfs:9000, e nada de fora do compose grava no bucket. O console web, na porta 9011 do seu computador, serve para você ver os objetos chegando.
  • Dois buckets, biblioteca e biblioteca-test. É o papel que o REDIS_PREFIX e o banco biblioteca_test já cumprem: a suíte grava e apaga à vontade sem tocar nas capas da aplicação.
  • As variáveis S3_* têm os nomes que o S3Client do Bun conhece. O passo 02 as lê explicitamente.
  • O storage-init cria os buckets. O S3Client do Bun lê, grava e apaga objetos, mas não cria buckets. A imagem do RustFS traz o rc, um cliente de linha de comando. Um serviço de tarefa única roda três comandos e termina; --ignore-existing faz a segunda execução não dar erro. A aplicação e os testes só sobem depois que ele termina bem (service_completed_successfully).
O /health responde cedo demais. Na primeira versão deste compose, o healthcheck usava /health, e o storage-init falhava com ✗ Network error: Service error: unhandled error (status: 503). O /health responde 200 assim que o processo sobe, mas a API S3 ainda devolve 503 nos primeiros segundos. O /health/ready só responde 200 quando ela aceita requisições.

O Bun traz um cliente S3 próprio, o S3Client, como trouxe o RedisClient na aula anterior: nada para instalar. Ele cobre o que a capa precisa:

O módulo de armazenamento

Crie backend/src/infrastructure/storage.ts: o cliente, a chave dos objetos e as quatro operações que a aplicação usa.

tsbackend/src/infrastructure/storage.ts
import { S3Client } from "bun";
import { ServiceUnavailable } from "../shared/errors";

/**
 * Cliente S3 do próprio Bun, apontando para o RustFS do compose. Sem S3_ENDPOINT
 * o cliente é null: as rotas de imagem respondem 503 e o resto da aplicação
 * funciona do mesmo jeito.
 */
export function createStorage(env: Record<string, string | undefined>): S3Client | null {
  if (!env.S3_ENDPOINT) return null;
  return new S3Client({
    endpoint: env.S3_ENDPOINT,
    accessKeyId: env.S3_ACCESS_KEY_ID,
    secretAccessKey: env.S3_SECRET_ACCESS_KEY,
    bucket: env.S3_BUCKET,
  });
}

export const storage: S3Client | null = createStorage(process.env);

/**
 * Toda chave de objeto passa por aqui. O bucket já separa a aplicação dos testes;
 * o primeiro trecho diz o módulo dono do objeto, como em redisKey(...).
 */
export function objectKey(...parts: (string | number)[]): string {
  return parts.join("/");
}

export type StoredObject = { stream: ReadableStream<Uint8Array>; type: string; size: number };

const UNAVAILABLE = "O armazenamento de arquivos está indisponível no momento";

function connected(client: S3Client | null): S3Client {
  if (!client) throw new ServiceUnavailable(UNAVAILABLE);
  return client;
}

/** Qualquer falha do RustFS (fora do ar, bucket inexistente, credencial errada) vira 503. */
function unavailable(error: unknown): ServiceUnavailable {
  const { code, message } = error as { code?: string; message?: string };
  console.warn("Armazenamento indisponível:", code ?? message);
  return new ServiceUnavailable(UNAVAILABLE);
}

/** Grava o objeto inteiro. Se a chave já existe, o objeto anterior é substituído. */
export async function putObject(key: string, bytes: Uint8Array, type: string, client = storage): Promise<void> {
  const s3 = connected(client);
  try {
    await s3.write(key, bytes, { type });
  } catch (error) {
    throw unavailable(error);
  }
}

/**
 * Lê os metadados (stat) e abre o fluxo de bytes; null se a chave não existe.
 * Não devolva new Response(s3.file(key)): o Bun responderia 302 para uma URL
 * assinada em rustfs:9000, um endereço que o navegador não alcança.
 */
export async function getObject(key: string, client = storage): Promise<StoredObject | null> {
  const file = connected(client).file(key);
  try {
    const { type, size } = await file.stat();
    return { stream: file.stream(), type, size };
  } catch (error) {
    if ((error as { code?: string }).code === "NoSuchKey") return null;
    throw unavailable(error);
  }
}

/** Apaga o objeto. Apagar uma chave que não existe também dá certo. */
export async function deleteObject(key: string, client = storage): Promise<void> {
  const s3 = connected(client);
  try {
    await s3.delete(key);
  } catch (error) {
    throw unavailable(error);
  }
}

/**
 * Limpeza depois do COMMIT: o registro já saiu do Postgres, então uma falha aqui
 * não desfaz nada. Vira um aviso no log, e o objeto fica órfão no bucket.
 */
export async function discardObject(key: string, client = storage): Promise<void> {
  if (!client) return;
  await deleteObject(key, client).catch(() => console.warn(`Objeto órfão no armazenamento: ${key}`));
}
  • Sem S3_ENDPOINT, o cliente é null. É o mesmo acordo do Redis: a aplicação sobe, e só as rotas de imagem respondem 503.
  • objectKey junta os trechos com barra, e o primeiro trecho diz o módulo dono do objeto: acervo/livros/7/capa é do Acervo. O bucket já separa a aplicação dos testes, então a chave não leva prefixo de ambiente.
  • Toda falha vira ServiceUnavailable (503), com o código do erro no log: RustFS fora do ar, bucket inexistente (NoSuchBucket) ou credencial errada. A única exceção é a chave que não existe: getObject devolve null, e quem chamou decide que isso é um 404.
  • discardObject nunca lança. Ele serve para a limpeza depois do COMMIT, quando o registro já saiu do Postgres e não há mais o que desfazer. Uma falha vira um aviso no log e um objeto órfão no bucket.
A armadilha do new Response(s3.file(key)). O Bun aceita um arquivo do S3 direto no Response, e parece o jeito mais curto de servir uma imagem. Só que ele responde 302 para uma URL assinada em http://rustfs:9000/..., um nome que só existe dentro da rede do Docker: o navegador não chega lá. Por isso o getObject faz o stat (para saber o Content-Type e o tamanho) e devolve o fluxo, e os bytes passam pelo backend.

A leitura da imagem

Crie backend/src/shared/images.ts: a detecção pela assinatura e a leitura do multipart, com os limites.

tsbackend/src/shared/images.ts
import { InvalidInput, PayloadTooLarge } from "./errors";

export const MAX_IMAGE_BYTES = 2 * 1024 * 1024;

export type ImageType = "image/jpeg" | "image/png" | "image/webp";

export type ImageUpload = { bytes: Uint8Array; type: ImageType };

function startsWith(bytes: Uint8Array, offset: number, expected: number[]): boolean {
  return expected.every((byte, i) => bytes[offset + i] === byte);
}

/**
 * O tipo vem da "assinatura" do arquivo, os bytes fixos do começo de cada
 * formato. O nome do arquivo e o Content-Type são escolhas de quem enviou e não
 * provam nada: um executável renomeado para .jpg chega como image/jpeg.
 */
export function detectImageType(bytes: Uint8Array): ImageType | null {
  if (startsWith(bytes, 0, [0xff, 0xd8, 0xff])) return "image/jpeg";
  if (startsWith(bytes, 0, [0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a])) return "image/png";
  // WebP é um contêiner RIFF: "RIFF" no byte 0 e "WEBP" a partir do byte 8
  if (startsWith(bytes, 0, [0x52, 0x49, 0x46, 0x46]) && startsWith(bytes, 8, [0x57, 0x45, 0x42, 0x50])) return "image/webp";
  return null;
}

/** Folga para as fronteiras e cabeçalhos do multipart, além da própria imagem. */
const MULTIPART_OVERHEAD = 64 * 1024;

/**
 * Lê uma imagem enviada como multipart/form-data no campo `field` e confere
 * tamanho e formato. Imagem grande demais é 413; qualquer outro problema, 400.
 */
export async function readImageUpload(request: Request, field: string): Promise<ImageUpload> {
  // recusa cedo, pelo cabeçalho, antes de ler um corpo muito maior que o limite
  if (Number(request.headers.get("content-length") ?? 0) > MAX_IMAGE_BYTES + MULTIPART_OVERHEAD) {
    throw new PayloadTooLarge("A imagem passa de 2 MB");
  }
  // formData() rejeita um corpo que não é multipart (um JSON, por exemplo)
  const form = await request.formData().catch(() => null);
  if (!form) throw new InvalidInput(`Envie a imagem como multipart/form-data, no campo ${field}`);
  const file = form.get(field);
  if (!(file instanceof File) || file.size === 0) throw new InvalidInput(`Envie a imagem no campo ${field}`);
  if (file.size > MAX_IMAGE_BYTES) throw new PayloadTooLarge("A imagem passa de 2 MB");

  const bytes = new Uint8Array(await file.arrayBuffer());
  const type = detectImageType(bytes);
  if (!type) throw new InvalidInput("Envie uma imagem JPEG, PNG ou WebP");
  return { bytes, type };
}

A ordem das conferências em readImageUpload é pensada:

  1. Pelo cabeçalho, antes de ler o corpo. Se o Content-Length já passa de 2 MB mais uma folga de 64 KiB (as fronteiras e os cabeçalhos do multipart), a resposta é 413 sem que o servidor leia um byte do arquivo.
  2. O corpo precisa ser multipart. Um JSON, por exemplo, faz o formData() rejeitar: 400.
  3. O campo precisa ter um arquivo não vazio: 400.
  4. O arquivo não passa de 2 MB: 413. O cabeçalho pode mentir ou faltar; o tamanho do arquivo não.
  5. A assinatura decide o tipo: JPEG, PNG ou WebP; qualquer outra coisa é 400. O tipo devolvido vem dos bytes, e é ele que vai para o RustFS.
Nunca confie no nome nem no Content-Type do cliente. Eles servem, no máximo, para a tela sugerir um filtro de arquivos. A decisão é do servidor, e pelos bytes. O WebP mostra por que olhar além do começo: RIFF sozinho também abre arquivos .wav e .avi.

Quando a capa mudou

Os bytes vão para o RustFS. O que o Postgres precisa saber? Só duas coisas: se o livro tem capa e quando ela mudou pela última vez. Uma coluna TIMESTAMPTZ que aceita nulo responde às duas: nula, o livro não tem capa.

A chave do objeto não vai para o banco: ela é fixa por livro (acervo/livros/{id}/capa) e se calcula a partir do id. Uma capa nova grava na mesma chave e substitui a anterior.

A data tem um segundo uso, no endereço da imagem. O JSON do livro ganha capaUrl com a data em milissegundos na query string:

MomentocapaUrl
livro sem capanull
depois do primeiro envio/api/livros/7/capa?v=1762956000000
depois de trocar a capa/api/livros/7/capa?v=1762956123456

A URL muda a cada troca, então o navegador pode guardar cada versão para sempre e nunca mostra uma capa velha. É o que o passo 05 aproveita no Cache-Control.

UC25: enviar, mostrar e remover a capa

A fatia manage-book-cover expõe três rotas. A imagem passa pelo backend nos dois sentidos (em produção, o caminho é outro; veja o fechamento):

RotaCorpoResposta
PUT /api/livros/:id/capamultipart, campo capa200 com o JSON do livro, já com capaUrl
GET /api/livros/:id/capa—200 com os bytes da imagem; 404 se o livro não tem capa
DELETE /api/livros/:id/capa—204

O difícil não é gravar; é manter dois armazenamentos coerentes sem uma transação que abranja os dois. O Postgres faz ROLLBACK; o RustFS não participa dele. A saída é escolher a ordem de modo que uma falha no meio deixe o estado menos ruim:

OperaçãoOrdemSe falhar entre um e outro
enviar1. grava o objeto · 2. grava a colunasobra, no máximo, um objeto que nenhum livro aponta
remover1. zera a coluna · 2. apaga o objetosobra um objeto órfão, e nenhum livro aponta para ele
(ordem errada)coluna antes do objeto, no envioo livro aponta para uma capa que não existe: imagem quebrada em toda tela

Um objeto órfão custa uns kilobytes de disco. Um livro apontando para o nada quebra a tela. A regra cabe numa frase: a coluna nunca promete um objeto que não existe.

/**
 * UC25: grava a capa no RustFS e depois marca no Postgres quando ela mudou.
 * Nessa ordem, uma falha no meio deixa no máximo um objeto sem uso no bucket,
 * nunca um livro apontando para uma capa que não existe.
 */
export async function uploadBookCover(
  id: number,
  image: ImageUpload,
  integration: CatalogIntegration,
  { client = storage, now = new Date() } = {},
): Promise<BookView> {
  // 404 antes de mandar qualquer byte para o RustFS
  await findBook(sql, id);
  await putObject(coverKey(id), image.bytes, image.type, client);

  const book = await inTransaction(async (tx) => {
    const [row] = await tx`
      UPDATE livros SET capa_atualizada_em = ${now} WHERE id = ${id}
      RETURNING id, isbn, titulo AS title, autor_id AS "authorId", data_catalogacao AS "catalogedOn"
    ` as BookRow[];
    return row ? toBookView(tx, row, integration, civilDate(now)) : null;
  });

    // o livro foi excluído enquanto a capa subia: o objeto não tem mais dono
    await discardObject(coverKey(id), client);
    throw new NotFound("Livro não encontrado");

  return book;
}

 * UC25: o Postgres diz se o livro tem capa; o RustFS guarda os bytes. Quem pede
 * a capa de um livro sem capa recebe 404 sem que o RustFS seja consultado.

export async function getBookCover(id: number, client = storage): Promise<StoredObject> {
  const [row] = await sql`SELECT capa_atualizada_em AS "coverUpdatedAt" FROM livros WHERE id = ${id}` as { coverUpdatedAt: Date | null }[];

import { discardObject, requireStorage, storage } from "../../../../infrastructure/storage";
import { inTransaction } from "../../../../infrastructure/transaction";
import { NotFound } from "../../../../shared/errors";
import { coverKey } from "../../infrastructure/covers";

/**
 * UC25: a ordem é a inversa do envio. Primeiro o Postgres esquece a capa; depois
 * o objeto sai do bucket. Se o RustFS falhar nesse último passo, sobra um objeto
 * órfão, mas nenhum livro aponta para ele.

export async function removeBookCover(id: number, client = storage): Promise<void> {
  // sem RustFS, 503 antes de mexer no banco
  requireStorage(client);
  const [row] = await inTransaction((tx) => tx`UPDATE livros SET capa_atualizada_em = NULL WHERE id = ${id} RETURNING id`);
  if (!row) throw new NotFound("Livro não encontrado");
  await discardObject(coverKey(id), client);
}

/** UC25: envia, mostra e remove a capa de um livro. A imagem passa pelo backend. */
export function registerRoutes(api: Hono): void {
  api.put("/livros/:id/capa", async (c) => {
    const id = parseId(c.req.param("id"));
    const image = await readImageUpload(c.req.raw, "capa");
    return c.json(bookJson(await uploadBookCover(id, image, catalogIntegration)));
  });

  api.get("/livros/:id/capa", async (c) => {
    const cover = await getBookCover(parseId(c.req.param("id")));
    // o fluxo vindo do RustFS sai em pedaços (Transfer-Encoding: chunked)
    return new Response(cover.stream, {
      headers: {
        "Content-Type": cover.type,
        // com ?v=..., a URL muda a cada troca de capa: o navegador pode guardar para sempre
        "Cache-Control": c.req.query("v") ? "public, max-age=31536000, immutable" : "no-cache",
        // o navegador usa o Content-Type informado, sem tentar adivinhar outro
        "X-Content-Type-Options": "nosniff",
      },
    });
  });

  api.delete("/livros/:id/capa", async (c) => {
    await removeBookCover(parseId(c.req.param("id")));
    return c.body(null, 204);
  });
}
  • Cache-Control depende do ?v=. Com ele, a URL muda a cada troca de capa, e o navegador pode guardar a imagem por um ano sem perguntar de novo (immutable). Sem ele, a mesma URL pode servir outra imagem amanhã: no-cache obriga o navegador a confirmar antes de reaproveitar.
  • X-Content-Type-Options: nosniff proíbe o navegador de "adivinhar" outro tipo pelo conteúdo. Junto com a assinatura do passo 03, um arquivo enviado como imagem nunca é interpretado como HTML ou script.
  • Sem Content-Length. O fluxo que vem do RustFS sai em pedaços (Transfer-Encoding: chunked), e o Bun descarta um Content-Length posto à mão nesse caso. Por isso a rota não o define.

export async function api<T>(path: string, options: RequestInit = {}): Promise<T> {
  let response: Response;
  try {
    response = await fetch(path, options);
  } catch {
    throw new Error("Não foi possível conectar à biblioteca. Verifique a conexão e tente novamente.");

      setFile(null); setPreview("");
      return;
    }
    setFile(chosen);
    setPreview(chosen ? URL.createObjectURL(chosen) : "");
  }

  async function run(action: () => Promise<unknown>, done: string, form?: HTMLFormElement) {
    setSending(true); setError(""); onStart();
    try {
      await action();
      setFile(null); setPreview(""); form?.reset();
      onChange(done);
    } catch (e) { setError((e as Error).message); }
    finally { setSending(false); }
  }

  function save(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    if (file) void run(() => sendFile(endpoint, field, file), `${Noun} enviada.`, event.currentTarget);
  }

  function remove() {
    void run(() => api(endpoint, { method: "DELETE" }), `${Noun} removida.`);
  }

  return <>
    <div className="image-manager">
      <figure className="image-current">
        {imageUrl ? <img src={imageUrl} alt={alt} /> : <div className="image-empty">Sem {noun}</div>}
        <figcaption>{imageUrl ? `${Noun} atual` : `Nenhuma ${noun} enviada`}</figcaption>
      </figure>
      <form className="record-form" onSubmit={save}>
        <Field name={field} label={imageUrl ? `Trocar a ${noun}` : `Escolher a ${noun}`} hint="JPEG, PNG ou WebP, até 2 MB.">
          <input id={field} name={field} type="file" accept={ACCEPTED} required onChange={choose} aria-describedby={`${field}-hint`} />
        </Field>
        {preview && <img className="image-preview" src={preview} alt="Pré-visualização da imagem escolhida" />}
        <div className="button-row">
          <button type="submit" disabled={sending || !file}>{sending ? "Enviando…" : `Enviar ${noun}`}</button>
          {imageUrl && <button type="button" className="danger" disabled={sending} onClick={remove}>Remover {noun}</button>}
        </div>
      </form>
    </div>
    <Notices error={error} />
  </>;
}
  • Thumbnail tem tamanho fixo e loading="lazy": numa lista longa, o navegador só baixa as capas que aparecem na tela. Sem capa, um espaço do mesmo tamanho mantém a tabela alinhada.
  • A pré-visualização é um endereço blob:, criado por URL.createObjectURL a partir do arquivo escolhido. Ela não sai do navegador, e o useEffect devolve a memória com revokeObjectURL quando a escolha muda.
  • A conferência de 2 MB na tela só poupa um envio. Quem decide é o servidor, pelos bytes. O accept do campo filtra a janela de arquivos, mas também não garante nada.
  • A mensagem de sucesso vai para a página, pelo onChange. Depois do envio, a página recarrega o livro; se a mensagem morasse no ImageManager, sumiria com a recarga. Pelo onStart, a página apaga a mensagem antiga quando o usuário escolhe outro arquivo ou começa um envio; sem isso, um erro novo apareceria ao lado de um "Capa enviada." que já não vale.

Solução de problemas

Quando algo não sobe

A porta 9011 já está em uso. Outro programa ocupa a porta do console, e o Docker recusa subir o rustfs. Troque o lado esquerdo do mapeamento em infra/compose.yaml, por exemplo "127.0.0.1:9012:9001", e abra o console em localhost:9012/rustfs/console/. O lado direito (9001) é a porta dentro do contêiner e não muda.

A aplicação ou a suíte não sobem por causa do storage-init. As duas esperam que ele termine bem. Veja o que ele disse e rode-o de novo:

terminalPowerShell
docker compose -f infra/compose.yaml logs storage-init
docker compose -f infra/compose.yaml up storage-init

Um status: 503 no log quase sempre é o healthcheck apontando para /health em vez de /health/ready (veja o passo 01).

O envio responde 503: "O armazenamento de arquivos está indisponível no momento". O log da aplicação (docker compose -f infra/compose.yaml logs app) mostra o motivo na linha Armazenamento indisponível:. NoSuchBucket quer dizer que o bucket não foi criado: rode o storage-init. Um erro de conexão quer dizer que o rustfs está fora do ar. Se a aplicação foi criada antes do passo 01, ela não tem as variáveis S3_*: recrie-a com docker compose -f infra/compose.yaml up -d --build app.

O console responde 403. Você abriu a raiz, localhost:9011/. O console mora em localhost:9011/rustfs/console/.

O S3Client não existe no módulo bun. É um Bun antigo. No seu computador, o projeto pede o Bun 1.4 ou mais novo: rode bun upgrade. No Docker, a imagem oven/bun:1-slim guardada em cache pode ser antiga; reconstrua buscando a mais nova: docker compose -f infra/compose.yaml build --pull app test.

Quando uma capa some

Depois de um down -v, as capas sumiram. O -v apaga os volumes: o pgdata e o rustfsdata vão juntos, e com eles os livros e as capas. Recrie o banco de testes (passo 00) e o seed.

O livro diz que tem capa, mas a miniatura fica em branco. A coluna e o bucket se desencontraram: só o RustFS perdeu os dados (o volume rustfsdata foi removido sozinho, ou alguém apagou o objeto pelo console). O GET da capa responde 404, Livro sem capa. Envie a capa de novo, ou remova-a, o que zera a coluna.

O que cada passo ensinou

PassoA ideia que fica
01o armazenamento de objetos é fonte da verdade: tem volume. O healthcheck precisa medir a prontidão da API, não só do processo
02um cliente fino, que transforma falhas em 503; a chave do objeto tem dono, como a tabela e a chave do Redis; um 302 para um endereço interno não serve ao navegador
03o tipo de um arquivo vem dos bytes, nunca do nome ou do Content-Type do cliente; grande demais é 413
04o Postgres guarda só o "quando"; a data na URL (?v=) derrota o cache velho do navegador
05sem transação entre dois armazenamentos, a ordem decide: a coluna nunca promete um objeto que não existe
06a limpeza que não deve derrubar o caso de uso roda depois do COMMIT e, se falhar, vira aviso no log
07o navegador escreve a fronteira do multipart; a pré-visualização é local (blob:); a tela confere só para poupar o envio

Em produção

Nesta aula, toda imagem passa pelo backend: é simples, e as regras ficam num lugar só. Em produção, o ideal é ter um subdomínio próprio de mídia (ex.: midia.biblioteca.com) servindo as imagens diretamente, por URLs assinadas de validade curta.

  • Os bytes saem do servidor da aplicação. Hoje, cada miniatura é uma requisição que abre um fluxo no RustFS e o repassa ao navegador. Com a URL assinada, o servidor só assina, e o armazenamento entrega.
  • Uma CDN na frente do subdomínio guarda as imagens perto de quem acessa.
  • Os cookies do domínio principal não viajam. Se os cookies de sessão forem host-only (sem o atributo Domain), eles não vão junto em cada pedido de imagem para o subdomínio de mídia.
  • A validade curta limita um vazamento. Uma URL copiada para fora deixa de funcionar em minutos.

O que mudaria no código: o GET da capa, em vez do fluxo, responderia 302 para s3.presign(chave, { expiresIn: 300 }). É o mesmo 302 que, no passo 02, era uma armadilha: lá, a URL assinada apontava para rustfs:9000, um nome interno. Em produção, o cliente S3 aponta para o endereço público do armazenamento, atrás do subdomínio de mídia, e a mesma URL passa a funcionar no navegador. O armazenamento ganha esse endereço público com HTTPS e, se o navegador também for enviar direto (uma URL assinada de PUT), o bucket precisa de uma regra de CORS que libere a origem da aplicação.

tsesboço, fora do projeto
// esboço: o GET da capa redireciona para uma URL assinada de 5 minutos
api.get("/livros/:id/capa", async (c) => {
  const id = parseId(c.req.param("id"));
  // ...confere no Postgres se o livro tem capa, como em getBookCover...
  const url = requireStorage().presign(coverKey(id), { expiresIn: 300 });
  return c.redirect(url, 302);
});

O que ficou de fora

  • Envio em partes (multipart upload). Para 2 MB, um único PUT basta. Vídeos e PDFs grandes pedem o envio em partes que o S3 oferece, com retomada se a conexão cair.
  • Miniaturas redimensionadas. Hoje, a miniatura de 48×64 baixa a capa inteira. Um serviço que gera versões menores (no envio ou sob demanda) economiza banda.
  • Varredura de órfãos. As falhas depois do COMMIT deixam objetos sem dono, avisados no log. Uma tarefa periódica pode listar o bucket e apagar as chaves sem livro.
